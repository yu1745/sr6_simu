# WebGPU 方案原型实测

设备：RTX 5070；浏览器报告 NVIDIA Blackwell，非软件回退。Chromium headless，本地运行。原始脚本 8.8 秒与 20 秒位姿；三维坐标平移到测试对附近以减小 float32 误差。WebGPU 独立计算，结果回读后交给 Three.js WebGLRenderer，未替换应用渲染器。

## 方案 A：FlexiCubes 距离场求交并提取网格

上游 commit `0dc0e4deef66640feb02e5601023358b1b92631f`，Apache-2.0。两个零件在同一网格域烘焙 GPU SDF，自写 max(A,B) compute 求交，然后调用上游 FlexiCubes 提取顶点/索引，作为 Three.js BufferGeometry 显示。

| 零件对 | 96 档单次总耗时 ms | WASM 参考体积 mm³ | GPU 体积 mm³ |
|---|---:|---:|---:|
| [38, 51] | 236.6 | 50.094681 | 46.421968 |
| [38, 61] | 175.7 | 18.697629 | 15.168210 |
| [19, 56] | 69.7 | 0.001858 | 0.000000 |
| [24, 57] | 177.2 | 1.813287 | 1.626398 |
| [19, 24] | 237.5 | 0.000000 | 0.000000 |
| [17, 49] | 30.8 | 0.015579 | 0.000000 |

单次包括两次烘焙、求交、提取和回读。96 为最长轴单元数，不是毫米精度。小交集漏检，明显交集低估；不选作当前机构的红色区域方案。没有进一步验证缓存距离场/自适应网格，因此结论仅针对本次原型配置。

## 方案 B：BVH 光线区间交集 → 颜色/深度 → Three.js

用现有 three-mesh-bvh 0.9.16 构建 BVH，自写 WGSL 遍历和区间求交，不是该库提供的现成布尔 API。每个像素求沿相机射线穿过两个封闭实体的内部区间交集，输出最近交集表面深度和红色标记，回读到 Three.js DataTexture，用 gl_FragDepth 与原场景合成。

| 零件对 | 640×640 热运行中位数 ms | 参考红色像素 | GPU 红色像素 | 像素交并比 IoU |
|---|---:|---:|---:|---:|
| [38, 51] | 5.9 | 5700 | 5695 | 0.9960 |
| [38, 61] | 6.1 | 1530 | 1533 | 0.9941 |
| [19, 56] | 4.8 | 72 | 71 | 0.9861 |
| [24, 57] | 6.3 | 3838 | 3843 | 0.9987 |
| [19, 24] | 5.0 | 0 | 0 | 1.0000 |
| [17, 49] | 5.4 | 2 | 4 | 0.5000 |

每个单对/分辨率运行四次，第一轮为冷启动，后三轮中位数；耗时为 compute 提交至 CPU 回读复制完成，不含一次性 BVH 构建/上传和后续 Three.js 纹理上传/绘制。初次 BVH 构建/上传约 1.6–19.3 ms。不能把单对像素原型数据当作整机帧率或直接与完整 WASM 检测耗时相比。

图像对照同一相机、相同分辨率、无抗锯齿：WASM 交集网格通过 WebGL 栅格化为参考红色掩膜。细小交集 [17,49] 仅 2 个参考像素而 GPU 4 个，不宣称完全精确；该对后来按用户约束排除。

增加保守包围盒交叠区域的屏幕裁剪，前四个正例 640 档像素任务占原全图 23%–31%。裁剪前后所有样本的红色像素及 IoU 完全一致。墙钟耗时未同比缩短，不能将工作量减少直接当作提速。

限制：当前原型只检查单对、单视角、相机在实体外；射线交点/栈各限制 64，本次无溢出。未完成相机进入零件、全场景多对批处理、遮挡/回读延迟及运动姿态同步验证。屏幕图像不提供完整的世界空间交集网格，不能用于导出体积或判定离屏零件是否干涉。

选择：淘汰当前 FlexiCubes 配置，保留 BVH + WGSL 路线作为显示加速原型。尚未替换主程序 WASM 检测，更没有发布。新的用户排除规则已独立应用于主程序。
